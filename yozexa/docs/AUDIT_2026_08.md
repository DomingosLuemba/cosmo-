# YOZEXA — internal audit, August 2026

Commit audited: `f50e13f`. Fixes landed in `28b847b`.

This audit attacked the running system. Every claim below was produced by
executing something against a live node, a real browser or the test suites —
not by reading code and judging it plausible. Where a check turned out to prove
less than it appeared to, that is recorded too, because a test that passes for
the wrong reason is worse than no test.

## Scope

| Area | Method |
|---|---|
| Key storage (CLI keyring) | 4 tamper attacks against an encrypted key file |
| Transaction authentication | 10 attacks: malleability, degenerate signatures, cross-chain, post-signature tampering, replay |
| Sequence control | Distinguished from CometBFT's mempool cache |
| Delegated spending (grants) | 14 attacks, including bypasses assembled by hand to skip SDK validation |
| Genesis and monetary terms | Hostile genesis construction |
| Supply and emission | Independent arithmetic against live state; series summation |
| Public node API | 29 malformed requests |
| Wallet key handling | Browser storage and network capture during wallet creation |
| Declared prohibitions | Static analysis across 37,480 lines |
| Dependencies | `npm audit`; `govulncheck` could not run (see Limitations) |

## Findings

### 1. Genesis did not enforce the founder and team vesting terms — High

The allocation table in `chain/app/genesis.go` names 500,000 YZXA to the
founder on a 2-year cliff and 8-year vest, and 800,000 to the team on
1-year/6-year. Those constants were referenced nowhere outside one test.
`Genesis.Validate` checked the total against the 10,000,000 supply cap and that
each schedule was internally coherent — and nothing tied a position to the
published terms.

Reproduced: a genesis declaring the `founder` category with 3,000,000 YZXA, a
one-second cliff and a two-second vest validated cleanly.

This is not an exploit — whoever writes a genesis controls it, and the file is
public. It is worse in a specific way: the numbers the whitepaper, the explorer
and the wallet all report were enforced by nothing, so an incorrect genesis
would have looked identical to a correct one to every automated check.

**Fixed.** A position claiming a reserved category must match the published
allocation, cliff and duration exactly, and a category may appear at most once
so the allocation cannot be split across several conforming positions. Networks
with no founder or team position — every devnet and testnet — are unaffected.

### 2. The wallet's lock did not erase the key — Medium

`lock()` called `unlockedKey.toBytes().fill(0)`. `toBytes()` returns
`Uint8Array.from(#scalar)` — a copy. The zeroing hit a throwaway buffer and the
private scalar stayed in memory until garbage collection, recoverable from a
heap snapshot of the tab. The idle lock exists for the shared-machine case,
which is exactly the case this weakened, while the module comment read
"Locking zeroes it".

**Fixed.** `PrivateKey.destroy()` wipes the scalar in place and makes the key
refuse to sign rather than sign with zeros; `lock()` calls it. `toBytes()`
still returns a copy deliberately, so inspecting a key cannot erase it — now
stated in the API and covered by a test that fails if it ever returns the
internal buffer.

### 3. Fiat rates passed through floating point — Low

`pay/src/quotes.ts` scaled a rate with `Math.round(price * 100 * 1e10)`. Above
roughly 9,007.2 units per YZXA that product exceeds 2^53 and stops being
exactly representable (measured: an error of 2 in 9.0087 × 10^15 at a price of
9008.7). The monetary effect is a relative error near 10^-16 and the quote
rounds up, so no merchant was ever short-changed.

The second half mattered more: the receipt reported `price.toFixed(10)` while
the amount was computed from the rate at 12 decimals. For prices below 10^-10
the two differed — measured at 5 × 10^-11, the receipt said 1 × 10^-10, double
the rate applied. A merchant could not reconcile a payment against its own
receipt.

**Fixed.** Price sources return a decimal string, scaled into integers exactly
with one documented rounding. A rate finer than the resolution kept is refused
rather than quoted against zero. The receipt reports the rate actually applied.
The wallet's price path and the SDK's `fiatReference` got the same treatment;
`fiatReference` accepts a string as well as a number, so nothing breaks.

### 4. A malformed address answered 404 — Low

`/v1/account/{addr}` and the address-keyed path queries returned "not found"
for input that was not an address. A wallet cannot distinguish a mistyped
address from an account with no history — which is how a typo becomes a lost
payment.

**Fixed.** Both return 400 with the parse error.

## What held

Each of these was attacked, not inspected.

**Key storage.** Four tamper attacks on an encrypted key file — wrong
passphrase, substituted address (the AEAD's associated data), a single flipped
ciphertext bit, a flipped salt byte — all refused, with one message that does
not reveal which check failed. The baseline signs, so the refusals are real and
not a broken key. Nothing on disk holds key material; the mnemonic is not
stored, only a flag saying one exists.

**Transaction authentication.** Ten attacks refused: a malleable high-S
signature (S replaced by n−S), r = 0, s = 0, a truncated signature, a signature
for `yozexa-mainnet-1` submitted to the localnet, an amount altered after
signing, a recipient altered after signing, replay, a negative amount, and an
amount above the supply cap.

**Sequence control.** The replay refusal above came from CometBFT's mempool
cache, which is bounded and evicts — so it proves less than it looks. Retested
with a *different* transaction reusing a spent sequence, which the cache cannot
catch: refused with `sequence 2 already used; account is at 3`. A sequence 50
ahead was refused as too far ahead.

**Delegated spending.** This is the strongest part of the system. Fourteen
attacks, including four assembled by hand to bypass SDK-side validation, all
refused by the chain: paying outside the recipient allow-list, exceeding the
per-period limit, exceeding the total, voting with the granter's stake,
granting itself more permission, nesting `exec` inside `exec`, using a grant
nobody issued, granting to itself, and signing as the granter without `exec`.
`spendProfile` refuses any message type not explicitly listed, so a message
type added later is denied to delegated keys until someone deliberately allows
it. Grants longer than a year, expiring in the past, or with a zero or negative
total are refused.

**Public API.** 29 malformed requests — 10 KB addresses, path traversal,
encoded nulls, negative and enormous heights, non-numeric limits, a 1 MB hash,
nested JSON 10,000 deep, a 5 MB body, wrong methods — produced no 5xx and no
crash. Request bodies are bounded at 128 KiB before decoding.

**Supply and emission.** All eight protocol invariants pass against live state.
Conservation holds: the sum of all balances equals circulating supply exactly.
The geometric emission series over 57 eras sums to 4,999,999,999,999,999,520,000,000
ayzxa — 480,000 ayzxa *below* the 5,000,000 YZXA reserve — and the code applies
two independent ceilings anyway.

**Wallet key handling.** A wallet created through the browser leaves nothing
secret behind: no mnemonic, no passphrase, no key in localStorage,
sessionStorage, cookies or IndexedDB. The stored vault holds only ciphertext,
salt, IV and the declared KDF and cipher, with 5.42 bits/byte of entropy.
Across 17 requests during creation, no request body carried secret material —
the wallet sends none at all.

**Declared prohibitions.** No floating point in chain balances. No `guaranteed`
outside a negation; no APY, ROI or referral language anywhere. No price written
into the code. No passport, name, phone, email, address or document field in
any on-chain type — an account holds address, balance, sequence and public key.
No secrets in the git history and no `.env` committed. No TODO, FIXME, mock,
stub or fake in any production path. Buy, Sell and Swap are disabled and each
states why.

## Not findings, but worth stating

**Webhooks have no replay cache.** Signatures are HMAC-SHA256 over
`timestamp.body`, compared in constant time, within a 300-second window — the
same design Stripe uses. A captured webhook can be replayed to the merchant
inside that window, which is why handlers must be idempotent. That is documented
and is the operator's responsibility, not a defect.

**`DELETE /v1/status` answers 200.** Read endpoints do not restrict the method.
Harmless — they are read-only — but untidy.

**Three high-severity npm advisories** reach the tree through Next 15: two
paths in postcss, one in sharp. Neither is reachable here: `next/image` is used
nowhere, so the sharp code path never runs, and no third-party CSS is processed
at runtime, so postcss only ever sees this project's own stylesheets at build
time. Clearing the advisories requires Next 16, a major upgrade. It should be
planned, because a scanner will flag a financial product regardless of
reachability.

## Limitations

**`govulncheck` could not run.** `vuln.go.dev` is blocked by this environment's
network policy. The Go dependency tree should be scanned outside the sandbox.
It is small: four direct dependencies — CometBFT 0.38.16, cometbft-db 0.14.1,
`decred/dcrd/dcrec/secp256k1/v4` 4.3.0, `btcsuite/btcd/btcutil` 1.1.6 — on Go
1.24.7.

**No cryptographic review of the primitives themselves.** secp256k1, scrypt,
XChaCha20-Poly1305, AES-256-GCM and SHA-256 are used as published, from
established libraries. This audit checked that they are applied correctly, not
that they are sound.

**No adversarial consensus testing.** Byzantine validators, network partitions
and long-range attacks were not simulated. Double-signing slashing is covered
by unit tests, not by a live multi-validator network under attack.

**Single-node testing.** Everything here ran against a one-validator localnet.
Multi-validator behaviour, sync from genesis and state-sync are untested.

**No load or economic testing.** Fee-market behaviour under congestion, and
whether the emission schedule secures the network at realistic valuations, are
open questions.

## Before mainnet

1. An external security audit. This one was done by the same party that wrote
   the code, which limits what it can be trusted to have found.
2. A public testnet with independent validators, running long enough to see
   real slashing, real governance and real upgrades.
3. `govulncheck` in CI, outside a restricted network.
4. Plan the Next 16 upgrade to clear the npm advisories.
5. A multi-validator adversarial test: partitions, double-signing, long-range
   attacks.
6. Publish the mainnet genesis for review before it is used. The rule added in
   finding 1 makes the founder and team terms machine-checkable; publishing
   lets anyone check the rest.
