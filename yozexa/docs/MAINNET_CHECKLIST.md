# YOZEXA Mainnet Checklist

Mainnet is not a milestone to hit on a date. It is a set of gates. Every one of
these must be **true**, not "in progress", before a network carrying real value
starts.

`yozexad init --network mainnet --with-genesis` deliberately refuses to run: a
mainnet genesis is assembled deliberately and reviewed by more than one person,
not generated by a convenience command.

## Gate 1 — the chain

- [ ] Every invariant passes continuously on a public testnet for 30+ days
- [ ] No SEV-0 or SEV-1 incident in the final 30 days of testnet
- [ ] Fuzzing has run for at least 100 CPU-hours per target with no new crashes
- [ ] Chaos tests pass: 30% of validators offline, 50% added latency, packet
      loss, slow disks, a full region outage
- [ ] Load tests published with real measurements, from a multi-region validator
      set, at 100 / 1,000 / 5,000 / 10,000 TPS offered load
- [ ] State sync and node restart verified from a cold start
- [ ] An upgrade has been executed on testnet through the governance path

## Gate 2 — audits

- [ ] Independent audit of the state machine, with emphasis on supply, mint,
      burn, vesting and staking accounting
- [ ] Independent review of the consensus integration and the ABCI boundary
- [ ] Independent audit of the wallet and key handling
- [ ] Every critical and high finding fixed and re-reviewed
- [ ] Audit reports published in full, including findings that were accepted
      rather than fixed, with the reasoning

No bridge and no smart contract VM ships without its own separate audit. See
[BRIDGE_SECURITY.md](BRIDGE_SECURITY.md) and
[SMART_CONTRACTS.md](SMART_CONTRACTS.md).

## Gate 3 — the genesis

- [ ] Allocation matches [TOKENOMICS.md](TOKENOMICS.md) exactly
- [ ] `yozexad genesis validate` passes
- [ ] Total minted at genesis + 5,000,000 emission reserve ≤ 10,000,000 YZXA,
      verified independently by at least two people
- [ ] Founder and team vesting schedules present, with the correct cliffs and
      durations
- [ ] No vesting position is also a validator operator
- [ ] Every module account address reproduced independently from the derivation
      rule
- [ ] Genesis file hash published and confirmed by every launch validator

## Gate 4 — validators

- [ ] At least 20 independently operated validators, across more than one legal
      jurisdiction and more than one hosting provider
- [ ] No single entity above the 33.4% veto threshold
- [ ] Every launch validator runs a sentry architecture
- [ ] Every launch validator has consensus keys in an HSM or remote signer
- [ ] Every launch validator has monitoring and alerting live and tested
- [ ] A rehearsed halt-and-restart drill completed on testnet

## Gate 5 — operations

- [ ] Monitoring covers blocks, validators, finality, forks, supply, inflation,
      fees, mempool, RPC latency and treasury operations
- [ ] Critical alerts configured: unexpected supply change, long fork, 33%
      validator failure, abnormal mint, unusual treasury operation, node version
      mismatch
- [ ] [INCIDENT_RESPONSE.md](INCIDENT_RESPONSE.md) rehearsed, not just written
- [ ] On-call rotation staffed
- [ ] Release binaries signed, checksummed, reproducible, with an SBOM

## Gate 6 — legal and product

- [ ] Legal review of the YOZEXA name and YZXA ticker completed; both are
      configurable in this codebase until that review is final
- [ ] Regulatory analysis complete for every jurisdiction where a **regulated**
      product is offered (custody, fiat exchange, cards, regulated settlement).
      The base network is permissionless; the products on top are not
      automatically so
- [ ] Company and treasury accounting formally separated
- [ ] No marketing material anywhere promises a return, a price, or a yield
- [ ] Every public metric distinguishes organic from incentivised volume
- [ ] Bug bounty live and funded from the security fund

## Gate 7 — the honest question

Before launch, one person must be able to answer each of these in writing:

1. If this network held one billion dollars tomorrow, which part would I be most
   worried about?
2. What is the largest amount that could be lost by a single bug we have not
   found, and what bounds it?
3. Which of our claims cannot currently be demonstrated by running the code?
4. What have we shipped that we would not personally put our own savings behind?

If any answer is uncomfortable, the answer to "are we ready" is no.
